01: Objective
Why this project exists

Peer-to-peer networking divides work across equally-privileged peers instead of relying on one central content host. The objective here was to build a working P2P application made of an index server plus a network of peers, capable of registering content, discovering it, downloading it, and removing it from the network again.

Each peer can act as a content server for files it owns and a content client for files it wants, at the same time: which is the property that makes a P2P network more resilient and versatile than a single client-server model.

02: Theory
Two protocols, two jobs

The design splits responsibilities cleanly along protocol lines, matching the right transport to the right kind of traffic:

  • UDP for control messages: registration, search, deregistration, and listing all go through the index server over UDP. These are small, latency-sensitive requests where occasionally losing a packet is an acceptable tradeoff for speed and low overhead.
  • TCP for file transfer: once a peer's address is found via the index server, the actual file transfer happens directly peer-to-peer over TCP, so large content moves reliably in ordered chunks.

Every message is wrapped in a simple PDU (Protocol Data Unit) struct: a one-character type field (R register, S search, T deregister, O list-online, D download, Q quit) plus a fixed-size data payload. The index server holds three parallel arrays (usernames, filenames, and addresses) that together form its content directory.

03: Implementation
Index server & peer logic

The index server runs a single UDP receive loop, dispatching on PDU type: registration checks for a free slot in the fixed-size library arrays before storing the entry, search scans the file-name array for a match and returns the owning peer's address, deregistration shifts all later entries left by one to close the gap, and listing concatenates every known filename into a single response.

if (rpdu.type == 'S') { for (; i < LIST_SIZE; i++) if (strcmp(search_tokens[1], movie_library[i]) == 0) break; if (i < LIST_SIZE) { strcat(spdu.data, "\n"); strcat(spdu.data, address_library[i]); } else { spdu.type = 'E'; strcpy(spdu.data, "Movie not found"); } }

The peer/client program is dual-role: it sends UDP requests to the index server to register, search, list, and deregister its own files, and it separately opens a TCP listener so other peers can connect and pull files directly. On a download request, the client resolves the target peer's address from the index server's search response, opens a TCP socket to that peer, and streams the file to disk in fixed-size chunks using a read/write loop.

04: Observations & Analysis
Strengths vs. weaknesses

Testing registration, search, listing, download, and quit confirmed the protocol works as designed. The design analysis surfaced a clear tradeoff profile:

Strengths

  • Clean separation of control (UDP) vs. data (TCP) simplifies each code path
  • UDP avoids connection-setup overhead for quick control messages
  • Modular operations (register, search, download, deregister) are easy to extend

Weaknesses

  • Minimal error handling: no retry/retransmission on UDP packet loss
  • Fixed-size arrays (LIST_SIZE) cap the number of files/users, hurting scalability
  • No encryption or authentication: usernames and filenames travel in plain text
  • Server processes requests sequentially, which could bottleneck under load
05: Conclusion
What the project proved

The client-server implementation successfully demonstrates a working file-sharing protocol with a clean split between UDP control traffic and TCP data transfer. It's simple enough to reason about end to end, which was the point of the exercise: but the same simplicity is exactly what limits it in a production setting.

To move this from a lab exercise to something robust, the clear next steps are: retry/timeout logic for lost UDP packets, dynamic data structures (linked lists or a real key-value store) in place of fixed arrays, TLS or a lightweight auth handshake for security, and either multithreading or async I/O on the server to handle concurrent peers without blocking. As delivered, it's a solid, working foundation for exactly those improvements.
