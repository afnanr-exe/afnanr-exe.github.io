Overview
What I built

Second project in a three-part Data & Systems Analyst portfolio, deliberately built with a different tool and domain than Project 1 (Databricks/PySpark logistics pipeline) to demonstrate range: Power BI Desktop, Power Query, and DAX, applied to construction project delivery instead of logistics.

Dataset is 300 rows from Hugging Face (JohnVans123/ProjectManagement): 100 construction projects with 3 tasks each, covering project type, location, schedule, status, priority, hours, budget, actual cost, and progress.

Build
Data model & dashboard

Cleaned the raw data in Power Query first: dates were stored DD/MM/YYYY and needed an explicit locale conversion (English UK) to stop them silently misparsing under a US locale, and a couple of numeric columns had reverted to text type and needed correcting.

Modeled the cleaned data as a star schema: DimProject (100 rows, project-level attributes) and FactTasks (300 rows, task-level attributes), joined one-to-many on Project ID. On top of that, wrote 9 DAX measures: Cost Variance %, Schedule Variance %, At Risk Tasks and At Risk %, Total Actual Cost, Total Budget, Cost Overrun ($), Total Tasks, and Average Progress.

The dashboard itself is a single interactive page: 4 KPI cards, a Budget vs Actual Cost trend by month, a task status breakdown, a Project Type × Region risk heatmap with a conditional-formatting gradient, and a Project Type slicer tying it all together.

Judgment
Key decisions

I initially assumed Location, End Date, and Priority were project-level fields, the natural assumption for a project-task hierarchy. Checking against the raw data showed they actually vary per task within a project, since one project can span multiple job sites. Rather than force those fields into the project dimension table through deduplication, which would have silently discarded roughly two-thirds of the real values, I kept them at task grain in the fact table instead, preserving 100% of the source data.

The dataset also had no planned-vs-actual date fields, so a literal day-count schedule variance would have meant fabricating data that doesn't exist. Instead, Schedule Variance % is built from the dataset's real Project Status field, an honest measure that reflects what the data actually supports rather than a metric that looks more precise than it is.

Analysis
Key findings
  • Actual cost ran roughly 69% under budget dashboard-wide, mostly explained by a high share of not-yet-started tasks sitting at $0 actual cost.
  • 29% of tasks belong to projects currently flagged "Behind" schedule.
  • 15% of tasks are both behind schedule and high priority, the true at-risk segment.
  • The risk heatmap surfaced Infrastructure projects in Ohio as the highest concentration of at-risk work in this sample.
Honesty check
Limitations

This is a small, example-style dataset, 100 projects, not live firm data, so findings are illustrative rather than production-grade. There's no contractor or subcontractor field, and Schedule Variance % is a status-derived proxy rather than a true day-level variance, a direct consequence of the source data not including planned dates.
